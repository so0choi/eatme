# 식재료 입력 레이어 (Ingredient Intake)

> 서비스 생존이 걸린 핵심 레이어. 입력 마찰을 최소화해 냉장고 상태를 실제와 일치시킨다.
> 초기 탐색 노트: [item-input.md](./item-input.md)

## 0. 최소 조건 = 재료당 3개 값

| 값 | 이유 |
|---|---|
| **품목** | 정체성·레시피 매칭 기준 |
| **가격** | 낭비 금액 통계(`lossAmount`)의 유일한 소스 (없으면 손실 리포트가 0원 처리) |
| **수량/중량** | 소비 추적·잔량·폐기량 |

목표: **이 3개를 최소 행동으로 확보.**

## 1. 아키텍처 — 입력 2모듈 + 공통 코어

```
[A. 자동입력]  ─┐
  커머스 어댑터   │
               ├─▶ DraftItem[] ─▶ [C. 정규화·커밋 코어] ─▶ Ingredient 저장
[B. 수동입력]  ─┘                    정규화 → 카탈로그 매칭 → shelf-life 추정 → 확인 → bulk 저장
  단일 인풋 파서
```

- A·B는 입력 *방식*만 다르고 결과물은 동일 → 변환·저장은 **C로 수렴**(중복 제거).
- 공통 타입(제안): `DraftIntakeItem { name, quantity?, unit?, price?, source, raw, confidence? }` — `@eatme/schemas`에 두어 web·api 공유.

## 2. B. 수동입력 — **구현 완료**

`/fridge/add`의 "빠른 입력". 한 줄에 하나씩 자연어로 입력하면 파싱해 일괄 등록. (클릭 5~6회 → 1회)

### 파일
| 파일 | 역할 |
|---|---|
| [parse-ingredient-input.ts](../apps/web/src/components/fridge/parse-ingredient-input.ts) | 파서 (품목·수량·가격) |
| [QuickAddForm.tsx](../apps/web/src/components/fridge/QuickAddForm.tsx) | 단일 인풋 + 실시간 프리뷰 + 보관/카테고리 컨트롤 |
| [actions/quick-add-ingredients.ts](../apps/web/src/components/fridge/actions/quick-add-ingredients.ts) | 파싱→검증→자동채움→일괄 저장 서버 액션 |
| [shelf-life-rules.ts](../apps/web/src/components/fridge/shelf-life-rules.ts) | 이름→보관위치·유통기한·카테고리 자동 추정 |

### 파싱 규칙
- 형식: `품목 수량 가격`. **쉼표 또는 띄어쓰기**로 구분(둘 다 지원), 줄바꿈 = 품목 구분.
- 경합(쉼표+띄어쓰기 혼용) 시 **쉼표 우선**.
- 앵커 기반 역할 식별: 가격(`원/만/천/백` 또는 맨 뒤 숫자), 수량(숫자+단위 `g/kg/개/…`), 나머지=품목.
- 단위 없는 숫자 기본 단위: **1~9 → 개(EA)**, **10 이상 → g(G)**.
- 한글 금액(`3천원`), 천단위 쉼표(`3,000`), 소수 수량(`1.5`) 처리.
- 보관위치·유통기한·카테고리는 `shelf-life-rules`로 자동 추정, UI에서 원클릭 변경.

### 안정성 (코드 리뷰 반영)
- 부분 실패 감지(`Promise.allSettled`) → 실패 라인만 남겨 **재시도 시 중복 저장 방지**.
- 검증 실패 라인도 조용히 버리지 않고 안내.
- IME 조합 중 Enter 제출 방지 (한글 마지막 글자 유실 방지).
- override는 라인 내용 기준 관리 → 줄 편집/재정렬에도 올바른 재료에 유지.
- 수량 소수 보존(`Float`), 가격만 정수 반올림.

## 3. A. 자동입력 — 쿠팡 주문메일 (설계 + 파서 구현)

### 배경 / 제약
- 쿠팡·네이버 모두 **공식 구매내역 API 없음**.
- 우회: 쿠팡이 보내는 **주문완료 이메일**을 Gmail에서 읽어 파싱.
  (네이버 아이디로 쿠팡을 쓰는 경우 네이버→Gmail 수신 설정으로 Gmail에 도착시킴)

### 대상 메일 필터 (실제 샘플 기준 확정)
- **발신자**: `noreply@e.coupang.com` (광고성 발신 주소와 구분됨)
- **제목**: `[쿠팡] …님 주문하신 내역을 확인해주세요.` → `subject:"주문하신 내역"`
- Gmail이 이 메일을 **`구매`(Purchases) 카테고리**로 자동 분류 → `category:purchases from:coupang` 도 강력.
- 예시 쿼리: `from:noreply@e.coupang.com subject:"주문하신 내역" category:purchases`

### 메일 본문 구조
상품 테이블: `구매 상세내역 | 쿠팡가 | 수량 | 구매금액 | 판매자`, `구매 상세내역`(헤더)~`결제 정보` 사이.
```
구매 상세내역              쿠팡가     수량  구매금액   판매자
소금집 관찰레, 120g, 1팩   12,800원   1    12,800원   쿠팡(주)
소금집 잠봉 햄, 120g, 1팩    8,900원   1     8,900원   쿠팡(주)
```
- **상품명이 콤마 구조**: `이름, 무게, 팩` → 무게(120g)가 이름 안에 있음 = "수량(무게)"의 소스.
- `구매금액` = 라인 실결제액(가격), `수량` 컬럼 = 팩 개수.

### 파싱 로직 (설계 — 프로토타입으로 검증, **코드 미반영**)
`parseCoupangOrderEmail(body)` 프로토타입으로 위 실제 샘플 파싱을 검증. 정식 코드는 기획 확정 후 백엔드 intake 어댑터로 반영.

결과 예시:
```json
[{ "name": "소금집 관찰레", "quantity": 120, "unit": "G", "price": 12800, "count": 1 },
 { "name": "소금집 잠봉 햄", "quantity": 120, "unit": "G", "price":  8900, "count": 1 }]
```
로직:
- `구매 상세내역`~`결제 정보` 사이 상품 행만 정규식 추출.
- 상품명 콤마 분리 → 이름 / 무게 / 팩. 수량 = 무게 × 수량컬럼.
- 가격 = `구매금액`.
- 참고: 현재는 렌더된 텍스트 기준. 운영에선 **HTML 본문**(중첩 테이블) 파싱이 더 안정적일 수 있어 실제 Gmail API 응답에 맞춰 확정.

### 남은 조각
| 단계 | 내용 | 상태 |
|---|---|---|
| 메일 수집 | Gmail API(`gmail.readonly`) 연동 — **백엔드** OAuth 스코프 확장 | 미구현 |
| **식품 분류** | 추출 품목 중 비식품 제거 (카탈로그/키워드 매칭 → 실패 시 LLM) | 미구현 |
| 정규화 | `CoupangItem` → `DraftIntakeItem`(source:'coupang') | 연결만 |
| 중복 방지 | 처리한 messageId 저장 (`ImportedEmail { userId, provider, messageId }`) | 미구현 |
| 확인 UI | 후보 목록 → 보정 → 일괄 저장(C 코어 재사용) | 미구현 |

---

## 4. 방향 C(부수) — 빼기(소비)도 입력

넣기만 줄이면 냉장고가 실제와 어긋남. 레시피 요리 시 자동 차감 / 유통기한 임박 확인 등. **후속 단계 별도 설계.**

## 5. 우선순위

1. 수동 빠른입력 + 공통 코어 (**구현 완료**)
2. 쿠팡 메일 파싱 로직 (**프로토타입 검증**) → 식품 분류 → Gmail 백엔드 연동 → 확인 UI
3. 추가 커머스 어댑터 / 소비 자동차감

## 6. 열린 이슈
- 식품 분류 방식 확정 (카탈로그+키워드 vs LLM vs 하이브리드)
- Gmail 연동을 백엔드(NestJS)에서 처리 (OAuth 스코프 확장, refresh token 저장)
- 네이버 구매내역 접근 방법(별도 조사)
- 개인정보(주문 메일) 저장 정책
- 동일 품목 재구매 병합 정책
